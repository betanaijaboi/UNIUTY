Security Requirements

Comprehensive security design for the UNIUTY Portal covering authentication hardening, biometric data protection, NDPR compliance, role-based access control, and incident response procedures.

Compliance Note: The UNIUTY Portal handles personally identifiable information (PII) for over 13,000 individuals and is subject to the Nigeria Data Protection Regulation (NDPR) 2019. All security measures documented here are minimum requirements, not optional enhancements.

1.3 Brute Force & Lockout Policy

  • Account locked after 5 consecutive failed login attempts
  • Lockout duration: 30 minutes (automatic unlock) or immediate admin unlock
  • Failed attempt counter resets on successful login
  • IP-level rate limiting: max 20 auth requests per minute per IP (Redis sliding window)
  • CAPTCHA presented after 3 failed attempts (hCaptcha — no Google dependency)
  • Locked account triggers email notification to user and alert to duty admin

1.4 Session Management

  • Sessions invalidated on: password change, role change, manual logout, account suspension
  • Concurrent session limit: 3 active sessions per user (oldest invalidated on new login)
  • Session metadata logged: IP, user agent, location (city-level), timestamp
  • Admin and VC sessions require biometric re-verification every 4 hours

2. Biometric Security

Critical: Biometric data is irreplaceable. Unlike passwords, a compromised biometric template cannot be "reset." Treat all biometric data with the highest classification level.

2.1 Storage & Encryption

  • Biometric templates are encrypted with AES-256-GCM before storage
  • Encryption keys managed by the application's Key Management Service (KMS) — never in source code
  • Templates are stored in an isolated, access-controlled database schema (biometric_vault)
  • Only the BiometricAPI service account has read access to the vault schema
  • Template hashes (SHA-256) are stored in biometric_log for audit purposes — never the raw template

2.2 Transmission Security

  • Biometric data is never transmitted in plaintext at any point in the system
  • Device-to-server communication encrypted via TLS 1.3 mutual authentication (mTLS)
  • Device certificates are provisioned and rotated annually by the ICT department
  • Template data in transit is additionally encrypted with a session-specific key derived via ECDH

2.3 Liveness Detection

  • All facial recognition captures must pass ISO 30107-3 Presentation Attack Detection (PAD) Level 2
  • Fingerprint sensors detect fake fingers using electrical skin resistance measurement
  • Failed liveness checks are logged separately as purpose: liveness_check_fail in biometric_log

2.4 Template Lifecycle

  • Templates are automatically deleted when a user account is permanently deactivated
  • Users may request template deletion under NDPR Article 17 — process completes within 72 hours
  • Deletion is cryptographically verified (secure erase, not soft delete)
  • Annual audit confirms no orphaned templates exist (templates without corresponding active users)

  • Database backups encrypted with a separate backup KMS key before offsite transfer
  • Redis is configured with TLS and ACL authentication; no sensitive data written without encryption

6. Audit & Logging

6.1 What Is Logged

The audit_log table captures every state-changing event in the system:

  • User authentication events: login, logout, failed login, password change
  • User management: account creation, role change, suspension, deletion
  • Result operations: submission, approval, rejection, amendment, publication
  • Biometric events: enrollment, verification, deletion (summary — full detail in biometric_log)
  • Payment events: payment initiated, gateway webhook received, reconciliation
  • Administrative actions: calendar changes, system config changes, bulk imports
  • Data exports: transcript downloads, report exports

6.2 Log Integrity

  • The audit_log table has no DELETE or UPDATE privileges granted to any application user
  • Each log entry includes a HMAC signature of its fields — detectable if records are tampered at DB level
  • Logs are also streamed in real-time to an external SIEM (Splunk or Elastic SIEM) for offsite copy
  • Log retention: 7 years (in line with Nigerian academic record retention guidelines)
