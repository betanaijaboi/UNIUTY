Deployment & Maintenance Plan

Infrastructure options, CI/CD pipeline design, environment configuration, monitoring setup, backup procedures, and rollback strategy for the UNIUTY Portal.

1. Hosting Infrastructure

Three hosting models are supported. The recommended default is Cloud (AWS Nigeria Region). On-premise is available for institutions with data sovereignty requirements.

2. CI/CD Pipeline

The pipeline is implemented with GitHub Actions. Every push to a feature branch triggers the quality gates; merges to main deploy to staging automatically; production deployments require a manual approval gate.

# .github/workflows/ci-cd.yml (simplified)

name: UNIUTY Portal CI/CD

on:
  push:
    branches: [main, develop, 'feature/**']
  pull_request:
    branches: [main]

jobs:
  # ─── Stage 1: Quality Gates ─────────────────────────────
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npm run lint          # ESLint + Prettier check

  unit-test:
    runs-on: ubuntu-latest
    needs: lint
    steps:
      - run: npm run test:unit     # Jest — coverage threshold 80%
      - uses: codecov/codecov-action@v4

  integration-test:
    runs-on: ubuntu-latest
    needs: unit-test
    services:
      postgres:
        image: postgres:16
        env: { POSTGRES_DB: uniuty_test, ... }
      redis:
        image: redis:7
    steps:
      - run: npm run test:integration  # Supertest against real DB

  security-scan:
    runs-on: ubuntu-latest
    needs: lint
    steps:
      - run: npm audit --audit-level high
      - uses: snyk/actions/node@master  # Dependency vulnerability scan

  # ─── Stage 2: Build ──────────────────────────────────────
  build:
    runs-on: ubuntu-latest
    needs: [integration-test, security-scan]
    steps:
      - run: docker build -t uniuty-portal:${{ github.sha }} .
      - run: docker push $ECR_REGISTRY/uniuty-portal:${{ github.sha }}

  # ─── Stage 3: Deploy to Staging ──────────────────────────
  deploy-staging:
    runs-on: ubuntu-latest
    needs: build
    if: github.ref == 'refs/heads/main'
    environment: staging
    steps:
      - run: kubectl set image deployment/api api=$ECR_REGISTRY/uniuty-portal:${{ github.sha }} -n staging
      - run: kubectl rollout status deployment/api -n staging
      - run: npm run test:e2e:staging  # Playwright smoke tests

  # ─── Stage 4: Production (manual approval required) ──────
  deploy-production:
    runs-on: ubuntu-latest
    needs: deploy-staging
    environment:
      name: production
      url: https://portal.uniuty.edu.ng
    # Requires manual approval in GitHub Environments
    steps:
      - run: kubectl set image deployment/api api=$ECR_REGISTRY/uniuty-portal:${{ github.sha }} -n production
      - run: kubectl rollout status deployment/api -n production

5.1 Recovery Procedure

  1. Declare incident via Slack #incidents and assign Incident Commander
  2. Assess: is this a partial failure (redirect to maintenance page) or full restore needed?
  3. For full restore: provision new RDS instance from latest snapshot
  4. Apply WAL logs to bring DB to RPO target (≤ 1 hour data loss)
  5. Update application DATABASE_URL environment variable to point to new instance
  6. Restart application containers; run smoke test suite
  7. Verify monitoring dashboards show healthy state
  8. Communicate to users via portal banner and email if recovery takes > 30 minutes
  9. Conduct post-incident review within 48 hours; update runbook

6.1 Biometric Hardware Maintenance Detail

  • Quarterly Calibration: ICT hardware specialist runs the BiometricAPI calibration routine per device; checks false rejection rate and false acceptance rate against baseline
  • Firmware Updates: Vendor firmware downloaded, tested on one terminal first, then rolled out to all terminals over 2 hours
  • Sensor Cleaning: Optical fingerprint sensors cleaned monthly with manufacturer-approved solution
  • Template Re-enrollment Trigger: If a device's FRR (False Rejection Rate) exceeds 5% post-calibration, affected users are flagged for re-enrollment

8. Rollback Procedure

The UNIUTY Portal uses a blue-green deployment strategy for production releases. At any time, both the current version (green) and the previous version (blue) are available, enabling instant rollback.

8.1 Blue-Green Strategy

Blue-Green: Two identical production environments run in parallel. Traffic is routed to "green" (active) via the load balancer. On a new deployment, "blue" receives the new version. After smoke tests pass, traffic switches from green → blue (new). The old green environment is kept warm for 24 hours for instant rollback.

8.2 Rollback Decision Criteria

  • Error rate > 5% within 15 minutes of deployment
  • P95 latency > 5 seconds sustained for 5 minutes
  • Any P1 security issue discovered post-deploy
  • Sentry error volume > 200% of baseline within 10 minutes
  • Manual decision by Project Manager or ICT Director

8.3 Rollback Steps

  1. ICT Director or Project Manager declares rollback in #incidents Slack
  2. DevOps engineer updates Kubernetes Deployment to previous image tag:
    kubectl set image deployment/api api=$ECR_REGISTRY/uniuty-portal:PREVIOUS_SHA -n production
kubectl rollout status deployment/api -n production
  3. ALB health checks confirm all pods healthy on previous version (typically < 90 seconds)
  4. Run smoke test suite to confirm rollback successful
  5. If DB migration was included in the bad deploy, run down-migration script:
    npm run migrate:down --steps=1
  6. Post incident Slack update: "Portal rolled back to vX.Y.Z — stable"
  7. Post-mortem scheduled within 48 hours; root cause identified before re-deploy

8.4 Canary Release (for Major Versions)

For major version releases (e.g. v1.0, v2.0), traffic is shifted gradually using Kubernetes traffic splitting:

  • 5% → 25% → 50% → 100% with 30-minute observation windows between shifts
  • Automatic rollback triggered if error rate exceeds threshold at any stage
  • This strategy allows real-user validation while limiting blast radius
